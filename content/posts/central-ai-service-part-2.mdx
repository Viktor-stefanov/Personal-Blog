# Central AI Service: configuration, alises and observability

_By Viktor Stefanov_

In the first part I described the problem we ran into while building our GenAI
platform and the shape of the solution we landed on. This part is about the
implementation: how the configuration is laid out, how aliases resolve, and what
we log to keep cost and latency visible.

![Central AI Service architecture: callers on the left reach a FastAPI endpoint, which resolves aliases against config.yml or config.test.yml, applies retry and error handling, routes to one of several Azure OpenAI instances, and logs to Application Insights](/assets/central-ai-service-architecture.png)

## 1. Zero-effort model switching

Every model update, and every use case that wanted to move a simpler task to a
smaller and cheaper model, produced the same ritual: change the code, open a PR,
wait for review, get approval, deploy to all the required environments. Once,
that's unremarkable. Thirty times, for the same one-line change, it's just
overhead with a Jira ticket attached.

The fix is unglamorous, which is rather the point. A base YAML file maps common
GenAI usage patterns to concrete models:

```yaml
aliases:
  default-chat: gpt-5
  summarization: gpt-4.1
  fast-chat: haiku-4.5
```

Note that the right-hand side isn't OpenAI-only. Foundry gives us Claude models
as well, and a cheap, fast chat alias is a good place for one. The caller never
finds out either way, which is rather the point.

The API contract then asks callers to name the alias they want, rather than a
model:

```json
{
  "alias": "default-chat",
  ...
}
```

Resolution is a map lookup against an in-memory copy of the config, done in a
middleware layer that runs before the request handler — no database call, no
extra network hop. When a new model beats the current `default-chat` in our
evaluations, we change the mapping once in the central service and every
consumer has it immediately, with nothing to do on their side.

### Overlays, for the cases that need to be different

Sooner or later a use case needs something other than the shared default —
pinning its summarization feature to one specific model version, say, because
its prompts were tuned against that version.

For those cases we added the idea of an **overlay configuration file**. An
overlay contains only the fields it wants to override from the base config:

```yaml
# default-chat-gpt-54.yaml
aliases:
  default-chat: gpt-5.4
```

The filename says what it changes. When a caller passes an overlay in the
request body, the service merges it on top of the base config at lookup time:

```json
{
  "alias": "default-chat",
  "overlay": "default-chat-gpt-54"
}
```

That caller resolves to `gpt-5.4`, while everyone else asking for `default-chat`
still gets `gpt-5`. Leave the field out and you get the base configuration.

Two things here look similar from the outside and are worth keeping apart.
Overlays are durable: a use case that needs to sit somewhere other than the
shared default carries its overlay in every request, for as long as it needs to.
Evaluating a candidate model before it becomes the default is a different
mechanism — the `config.test.yaml` and request header from part one — and that
one is meant to be thrown away once the evaluation is done. We keep them
separate on purpose. Merge the two and every experiment eventually turns into
permanent configuration that nobody remembers agreeing to.

### What this costs at runtime

At startup the service loads every overlay file and merges each one with the
base config, so what sits in memory is a fully resolved map per overlay. Memory
is O(N) — the base config plus N overlays — and a lookup is two map accesses,
`config["default-chat-gpt-54"]["default-chat"]`, so O(1). Even with far more
overlays than we expect to ever have, neither number is worth optimising.

## 2. Logging and cost tracking

With 30+ use cases behind one service, the logs have to answer two questions at
any hour of the day: is the service healthy, and who is spending what?

### What we log

Every request that passes through the service emits a single structured log
entry.

- **Who's calling.** Each request body carries a use case identifier —
  `"use_case": "invoice-summarizer"` — which we pull out early in the request
  lifecycle and attach to every subsequent log record for that request. One log
  line is enough to get back to the consumer that produced it.
- **Alias and model.** We log both the alias the caller asked for
  (`summarization`) and the concrete model it resolved to (`gpt-4.1`). Keeping
  both matters when a model gets swapped behind an alias: you want to line up a
  change in behaviour or cost with the exact moment the mapping changed, rather
  than reconstruct it weeks later.
- **Token counts.** Prompt and completion tokens separately, as the provider
  reports them. Every major provider prices the two differently, and a single
  total quietly throws away information you will eventually want back.
- **Cost.** Computed from the token counts in the provider response against an
  internal price table keyed by model name. It happens in the service, so no
  consumer needs to know or care what anything costs per thousand tokens.
- **Latency.** Wall-clock time from the request entering the service to the
  response leaving it, measured at the middleware level, so alias resolution,
  provider round trip and serialisation are all inside the number.
- **Request and response payloads.** The full message array and the provider
  response. Verbose, yes — and worth it. When a use case reports that a model
  did something strange, having the exact payload ends the discussion instead of
  starting one. Retention policies and dashboard filters keep it from drowning
  out everything else.

### Implementation

Nothing exotic: Python's standard `logging` module writing structured JSON
records. They went to Application Insights first, which is still what the
diagram above shows, and we have since migrated to Grafana. The records
themselves didn't change for the migration — only what reads them, which is the
argument for structured logging in one sentence. No custom logging framework
either, and no third-party SDK. The structure is what makes it useful — every
field above is its own key in the JSON object, not a fragment buried in a
free-text message.

```python
logger.info("request_completed", extra={
    "use_case": use_case_id,
    "alias": alias,
    "model": resolved_model,
    "prompt_tokens": usage.prompt_tokens,
    "completion_tokens": usage.completion_tokens,
    "cost_usd": computed_cost,
    "latency_ms": latency,
})
```

One record per request means one Grafana query gives you cost by use case, token
burn by model, or p95 latency over the last 24 hours — no joins, no
post-processing.

### Cost tracking

The price table lives in a YAML file next to the base configuration:

```yaml
pricing:
  gpt-5:
    prompt_per_1k: 0.0025
    completion_per_1k: 0.0100
  gpt-4.1:
    prompt_per_1k: 0.0020
    completion_per_1k: 0.0080
  haiku-4.5:
    prompt_per_1k: 0.0001
    completion_per_1k: 0.0005
```

Cost is computed after every successful provider response:

```python
def compute_cost(model: str, usage: Usage) -> float:
    pricing = config["pricing"][model]
    prompt_cost = (usage.prompt_tokens / 1000) * pricing["prompt_per_1k"]
    completion_cost = (usage.completion_tokens / 1000) * pricing["completion_per_1k"]
    return prompt_cost + completion_cost
```

When a provider changes its prices, there is exactly one line to edit. Every use
case shows the corrected figures in Grafana without a single line of application
code moving. It's the same idea as model aliasing, applied to money: keep the
configuration in one place and let the consumers stay unaware of it.

### What we get out of it

The dashboards we actually keep open:

- **Cost by use case**, broken down by day — who is driving the spend
- **Token efficiency**, as the prompt-to-completion ratio per use case, which is
  a reliable way to notice a system prompt that has quietly grown too long
- **Model distribution** across traffic, which is the first thing we look at
  after rolling out an alias change
- **Error rates and latency percentiles**, p50/p95/p99 per endpoint, with use
  case as a filter

None of this needed a dedicated observability platform or a metrics pipeline of
its own. Structured logging into Grafana, done the same way everywhere, covers
most of what engineering and the business actually ask us.

Looking back, the striking thing is how little of this was clever. Alias
resolution is a map lookup. Cost tracking is a multiplication. What made both
worth building was putting them in one place, once, instead of 30 times.
